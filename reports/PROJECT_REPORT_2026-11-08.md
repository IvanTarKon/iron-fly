# Отчёт по проекту «Железная муха»

**Дата:** 8 ноября 2026 года.  
**Объект отчёта:** программное управление движением шестиногого робота с 18 суставами, физическая симуляция и интерфейс экспериментов.  
**Текущий результат:** работающий виртуальный прототип на демонстрационной геометрии. Реальный робот и полный алгоритм с датчиками ещё не приняты.

## 1. Результат этапа

Проект доведён от экспериментальной оболочки над готовым ядром до управляемой физической симуляции с браузерным интерфейсом. Пользователь может наблюдать исходную трёхмерную модель, задавать направление и скорость движения, выбирать походку, менять параметры поверхности и камеры, останавливать движение и создавать новую сцену.

Основой остался готовый стек Hexapod. Кинематика, генераторы походок и автомат движения не переписывались. Основная работа выполнена в адаптере, проверках и интерфейсе. В ядро внесён один небольшой документированный патч проверки допустимости целой позы.

| Область | Состояние |
|---|---|
| Прямая и обратная кинематика 6 × 3 DoF | Переиспользованы из исходного ядра; проверены на демонстрационной модели |
| Tripod, Wave, Ripple | Доступны в контроллере и интерфейсе |
| Движение по X/Y и поворот | Подтверждены физическими сценариями на низких скоростях |
| Остановка, ошибки команд, повторный запуск | Реализованы и покрыты тестами |
| PyBullet и исходная URDF | Подключены через публичный MotionController |
| Браузерный интерфейс WebGL | Работает; при проверке отображал 60 кадров/с |
| Ручной ввод параметров | Реализован, включая дробные числа и проверку диапазонов |
| Фоновый сервер | Отдельная пользовательская служба systemd |
| IMU/Fusion, контакты и горизонтирование | Не реализованы |
| Физический вывод и испытания на Repka Pi | Не выполнены |

## 2. Архитектура и переиспользование

Путь управления:

**Интерфейс → локальный сервер → MotionController → C++ Hexapod-Firmware → адаптер симуляции → PyBullet.**

Обратный путь отображения:

**PyBullet → измеренные положения корпуса и суставов → браузер → WebGL.**

Целевые углы контроллера выводятся отдельно от измеренных положений модели. Отрисовка не участвует в расчёте физики.

| Компонент | Назначение | Закреплённая версия |
|---|---|---|
| Hexapod-Simulation | Мост к C++ и среда симуляции | `fc03ebf8b222031c40dc003c95f96d7f96302cf9` |
| Hexapod-Firmware внутри Simulation | FK/IK, походки, траектории, автомат Robot | `82d94e01df3e977c624bb671db4933b5fa1e572c` + локальный патч |
| Hexapod-Controller | Клиент команд и протокол | `0f68c0c15e1d194675c294022baa5efbade28f6a` |
| Hexapod-Hardware | URDF и STL-детали | `f8ee8084d48470283d5ca23394d5a4b9590ad9e8` |

Самостоятельная копия Firmware в vendor используется для сравнения; рабочее ядро берётся из подмодуля Simulation. Соответствие четырёх версий и локального патча повторно проверено при подготовке отчёта.

По локальному реестру THIRD_PARTY программные компоненты имеют GPL-3.0, модель Hardware — CERN-OHL-W-2.0. Исходные лицензии сохранены. Fusion, forgevolt, OpenSHC и Mithi в текущую реализацию не включены; их пригодность для следующего этапа ещё предстоит проверить.

## 3. Выполненные изменения

### Контроллер и координаты

Внешний API использует метры, секунды и радианы. Порядок выходов — LF/LM/LR/RF/RM/RR, по три сустава coxa/femur/tibia на ногу. Преобразование к исходному порядку каналов, направлениям и нулям сервоприводов вынесено на границу адаптера.

Установлено, что ядро считает направлением вперёд +X, а исходная URDF — +Y. Разница компенсирована ориентацией модели при загрузке. Проверены движения при начальном yaw корпуса 0° и 90°.

`stop` прекращает ходьбу с сохранением стойки. Ошибочная или просроченная команда блокирует движение до нового `start`. При некорректном dt цикл симуляции продолжает обработку с резервным шагом 20 мс. Смена походки через интерфейс выполняется после остановки. Прекращение исполнения самого процесса не покрывается этим программным тайм-аутом.

### Проверка целой позы

При исходном подъёме femur запрашивал угол примерно на 0,021° выше предела 90° в двух кадрах. Независимая обрезка суставов скрывала расхождение между требуемым и фактическим положением стоп.

Локальный патч отклоняет целую недопустимую позу, удерживает предыдущую и предоставляет диагностику отклонения. Штатные кинематика, походки и последовательность подъёма сохранены. При отклонении позы во время активного движения адаптер запрещает дальнейшее движение до повторного разрешения.

### Интерфейс и пределы

Доступны запуск и остановка ходьбы, пауза физики, повторное разрешение движения, выбор походки, новая сцена, изменение трения и гравитации, начального угла корпуса и ракурса камеры.

Числа можно вводить вручную или менять ползунками. Пустые поля и значения вне диапазона отклоняются. Дробный ручной ввод сохраняется без округления к шагу ползунка.

Текущие ограничения скорости взяты из `config/demo.yml`:

| Параметр | Допустимая команда |
|---|---:|
| Скорость по X | −300…+300 мм/с |
| Скорость по Y | −300…+300 мм/с |
| Скорость поворота | −60…+60°/с |
| Высота стойки | 80 мм, фиксирована |

Линейные пределы применяются к каждой оси отдельно, как в исходном ядре. Это пределы команды, а не гарантия фактической скорости: генератор ограничивает движение также параметрами шага. Полная проверка устойчивости на максимальных скоростях не проведена.

## 4. Испытания и доказательства

### Повторно выполнено для текущего кода

| Проверка | Результат |
|---|---|
| Тесты MotionController | 8 из 8, код завершения 0 |
| Тесты интерфейса и движка | 3 из 3, код завершения 0 |
| Проверка закреплённых исходников и патча | Успешно, код завершения 0 |
| Доступность сервера | HTTP 200, ready=true, состояние IDLE |
| Состояние службы | active/running; автоперезапуск on-failure |

Тесты включают обработку отказов, повторный запуск, отображение каналов, конфигурационные границы скорости, отклонение неверных настроек, соответствие URDF-иерархии измеренным положениям звеньев PyBullet, смену походки, паузу и сброс сцены. Проверяется также отсутствие вызовов CPU-рендерера в движке сервера.

В браузере отдельно проверены ручной ввод 100,5 мм/с, применение параметра, движение и остановка. Ввод 301 мм/с был отклонён. Это функциональная проверка интерфейса, а не аттестация полного диапазона скоростей.

### Сохранённые результаты предыдущего этапа

Физическая матрица содержит **36 успешных сценариев**: три походки × два начальных угла × шесть направлений. Скорости испытаний — 30 мм/с при поступательном движении и 0,15 рад/с при повороте. За 6 модельных секунд получено перемещение 0,155–0,185 м либо поворот 0,769–0,826 рад в заданную сторону.

Критерии включали направление движения, ограничение поперечного отклонения, сохранение высоты и наклона корпуса, а также малый дрейф после остановки. В расширенных сценариях проверялись ошибки команд и смены походок.

C++-проверка охватила 75 600 целей ног. В исследованной матрице не обнаружены недостижимые цели или недопустимые записи углов. Максимальная вычислительная ошибка FK(IK) составила около 0,000077 мм; это численная согласованность алгоритмов, а не точность реальной механики. На подъёме выявлены 216 потенциально обрезаемых суставных целей в 36 целых позах; после патча эти позы отклонялись полностью.

**Граница применимости:** хеш MotionController в сохранённом отчёте 36 сценариев отличается от текущего после расширения скоростных пределов. Полная матрица в рамках подготовки этого отчёта не повторялась. Её результаты нельзя распространять на весь новый диапазон 300 мм/с и 60°/с.

### Исходные upstream-тесты

Исходный `test_robot` сохраняет 25 ошибок; остальные четыре исходных набора проходили. Аудит показал, что 22 из 25 ошибок исчезают при поддержании heartbeat в тестовом ожидании. Три исходных расхождения связаны с записью начальной позы, поведением watchdog и низким напряжением. После устранения каскадного влияния watchdog проявляется ещё одна ранее замаскированная проверка отключения питания при низком напряжении.

Исходные тесты не отключались и не заменялись диагностическим вариантом. Сохранённый общий результат имеет DEMO_EXIT=0 и UPSTREAM_EXIT=1. Полная upstream-приёмка не объявляется.

## 5. Производительность и работа сервера

Первый интерфейс передавал PNG-кадры, отрисованные на CPU. Это ограничивало частоту примерно до 2–3 кадров/с и замедляло ход модельного времени.

После переноса отрисовки в WebGL браузер загружает исходные детали один раз и получает только состояния модели. Обновления интерполируются с задержкой около 80 мс; отображение ограничено 60 кадрами/с. В браузерной проверке во время ходьбы наблюдались 60 кадров/с без ошибок WebGL.

| Показатель | Прежний PNG-интерфейс, стойка | WebGL-интерфейс, ходьба |
|---|---:|---:|
| CPU процесса сервера | около 61% одного ядра | 12,4% одного ядра |
| RSS сервера | около 283 МиБ | 270,4 МиБ |
| Модельных секунд за реальную секунду | 0,544 | 0,995 |

Это короткие пятисекундные замеры на текущем компьютере, а не длительное нагрузочное испытание. Режимы сравнения различаются. Ресурсы браузера и GPU не включены: часть нагрузки перенесена с сервера в браузер. Эти цифры не являются прогнозом для Repka Pi.

Предыдущий сервер завершился с кодом 143, соответствующим SIGTERM. Python-исключения в сохранённом выводе не было; отправитель сигнала не установлен. Для независимости от временной сессии запуска создана пользовательская служба `muha-simulation.service` с перезапуском при аварии через 2 с и журналом systemd.

При подготовке отчёта служба активна, интерфейс отвечает по адресу **http://127.0.0.1:8766/**. Сервер слушает только локальный адрес. Автозапуск после перезагрузки компьютера не настроен; параметры сцены хранятся в памяти и сбрасываются при перезапуске.

## 6. Оставшиеся работы и следующий этап

1. **Аттестовать повышенные скорости.** Проверить выбранные скорости вплоть до конфигурационных пределов для каждой походки, отдельные и смешанные команды, торможение, достижимость, суставные скорости и ускорения. Определить рабочую область по результатам измерений.
2. **Подставить реальную механику.** Получить размеры, крепления, ограничения, массу и центр масс; согласовать вычислительную геометрию с URDF. Сейчас контроллер намеренно принимает только закреплённый демонстрационный профиль.
3. **Добавить ориентацию и горизонтирование.** Проверить и подключить Fusion, калибровку IMU и ограниченную коррекцию roll/pitch. Первые испытания выполнить на записанных и синтетических данных.
4. **Добавить контакты и устойчивость.** Реализовать обработку касания, поиск опоры, оценку опорного многоугольника и положения центра масс; проверить реакцию на потерю контактов.
5. **Подключить аппаратный уровень.** После получения схемы каналов и калибровки реализовать адаптер PCA9685 и провести стендовые испытания. Измерить время цикла и ресурсы на Repka Pi совместно с другими подсистемами.
6. **Закрыть воспроизводимость и приёмку.** Повторить установку в чистом окружении, выполнить полную регрессию и оформить отдельные критерии программной и аппаратной готовности.

Срок завершения этих работ не уточнялся: фактические трудозатраты не учитывались, а механические и аппаратные исходные данные ещё не подтверждены.
