# Железная муха — виртуальный демонстрационный контроллер

**Начните здесь:** [первый запуск без опыта](docs/FIRST_START.md) · [управление и интеграция](docs/CONTROL_GUIDE.md) · [краткий API мозга](BRAIN_API.md).

Инструкции обновлены 16 ноября 2026: кнопочное управление и API отдельного мозга, базовая скорость 100 мм/с, ускорение 150 мм/с. Целевая платформа — Repka (модель/ОС ещё не выбраны); дополнительный путь — Windows через WSL. Аппаратный вывод пока не реализован.

Готовое ядро Hexapod-Firmware адаптировано через `MotionController` к исходной
модели PyBullet. Используются существующие FK/IK, Tripod/Wave/Ripple, протокол
и автомат Robot. Это проверка виртуального MVP, не приёмка реального робота.
Fusion, контакты, горизонтирование и физический вывод отсутствуют.

## Быстрый запуск интерфейса

```sh
git clone https://github.com/IvanTarKon/iron-fly.git
cd iron-fly
bash scripts/bootstrap.sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
bash scripts/build.sh
.venv/bin/python scripts/simulation_ui.py --port 8766
```

Откройте http://127.0.0.1:8766. Для запуска через службу systemd: `bash scripts/server.sh start`.

## Установка и запуск

Нужны Python с venv, g++ с C++17 и Git. Проверенное окружение: Python 3.14.9,
текущая проверка — Python 3.14.10,
Linux x86_64, зависимости из `requirements.txt`.

```sh
bash scripts/bootstrap.sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
bash scripts/check.sh --demo-only
```

Полный запуск проверяет версии, собирает мост, запускает исходные тесты,
аудит их расхождений, тесты адаптера, C++ проверку траекторий и 36 сценариев
PyBullet (3 походки × 2 начальных yaw × 6 направлений). В трёх сценариях также
проверяются физическая остановка после ошибок, повторный запуск и смена походок.
Результаты и коды возврата записываются в `reports/`.

`--demo-only` возвращает 0 при успехе собственных проверок, **но сохраняет и
показывает ненулевой код upstream**. `bash scripts/check.sh` без аргумента
работает строго и возвращает 1 из-за 25 известных ошибок исходного test_robot.
Не использовать успех demo-only как полную upstream-приёмку.

Можно использовать готовое окружение: `PYTHON=/absolute/path/to/python bash scripts/check.sh --demo-only`.
Для короткого прогона после сборки:

```sh
bash scripts/build.sh
.venv/bin/python scripts/sim_probe.py --quick
```

При восстановлении vendor следовать SHA в `THIRD_PARTY.md` и рекурсивно
инициализировать подмодули Simulation. Затем **один раз** применить наш патч:

```sh
git -C vendor/Hexapod-Simulation/Hexapod-Firmware apply ../../../patches/0001-reject-whole-pose.patch
```

В поставленной рабочей копии патч уже применён. `scripts/verify_sources.py`
проверяет SHA и точное соответствие изменения сохранённому патчу. Не обновлять
подмодули на последние версии. Для чистой копии используйте `bash scripts/bootstrap.sh`.

## API и ограничения первого рубежа

```python
from motion import MotionController, get_motion_command
c = MotionController()
output = c.update_motion(get_motion_command(c.time, 'start'), 0.02)
# Продолжать цикл 50 Гц; дождаться output.state == 'IDLE'.
output = c.update_motion(get_motion_command(c.time, 'move', vx=0.03), 0.02)
output = c.update_motion(get_motion_command(c.time, 'stop'), 0.02)
```

Добавить `src` в PYTHONPATH. Все внешние длины — метры, углы — радианы,
время — секунды. +X вперёд, +Y влево, +Z вверх. Timestamp относится к логическим
часам конкретного контроллера **на входе** в update; текущая команда создаётся
с `c.time`. Часы другого процесса напрямую использовать нельзя.

- `start` явно разрешает движение и запускает штатный подъём при необходимости.
- `move` задаёт скорости. Пределы берутся из safety в config/demo.yml: |vx| и |vy| ≤0,3 м/с
  по каждой оси отдельно, |yaw_rate|≤π/3 рад/с (60°/с), высота ровно 0,08 м.
  Это пределы команды; достижимая скорость ограничивается также длиной шага и походкой.
  Повышенные скорости экспериментальны; матрица 36 сценариев проверяла 0,03 м/с и 0,15 рад/с. Полная физическая матрица проверяет
  отдельные оси; произвольные смешанные движения отдельно не аттестованы.
- `stop` обнуляет скорость через штатное сглаживание, сохраняет питание и разрешение.
- Возраст команды >0,5 с, будущее время, неверные данные или выход за область
  блокируют движение до нового корректного `start`. Цикл продолжает исполняться.
- Неверный `dt` обрабатывается как отказ команды; ядро получает резервный шаг 0,02 с.
  Это правило симуляции, а не измерение фактически прошедшего времени.
- `gait='tripod'|'wave'|'ripple'`. Менять походку можно только в OFF/IDLE.
  Попытка переключить на ходу вызывает остановку и требует `start`.
- При FAULT автоматическое возобновление запрещено. Если вызовы update прекратятся,
  этот программный цикл ничего не выполнит; аппаратную защиту он не заменяет.

Выход: 18 кинематических углов в порядке LF/LM/LR/RF/RM/RR, внутри ноги
coxa/femur/tibia; строка `state`, `diagnostic`, `timestamp`, `valid`, `armed`,
`powered`, `gait`, `pose_rejected`, `rejected_poses`. Это цели, не измерения.
`valid` описывает выдаваемые углы; при отклонении новой позы предыдущая целая
поза может оставаться допустимой. `pose_rejected` явно обозначает такое удержание.
В активной ходьбе отклонение позы также блокирует дальнейшее движение.

Конфигурация проверяется до создания ядра: секции kinematics/hardware/safety/gaits
должны совпадать с закреплённым upstream-профилем. Это намеренное ограничение
демонстрации, а не поддержка произвольной механики. Настройки serial не используются.
Глобальные параметры upstream общие внутри загруженной библиотеки; разные
геометрии в одном процессе не поддерживаются.

## Координаты и единственный патч ядра

URDF смотрит вперёд по +Y. Поэтому при заданном yaw корпуса модель загружается
с yaw−π/2; углы суставов не переставляются ради компенсации этой разницы.
SimulationSink проверяет имена и порядок 18 суставов и переводит выход API
обратно в исходные servo-space градусы для готового BulletInterface.

В исходном подъёме femur превышал предел 90° примерно на 0,021° в двух кадрах.
Патч `resolve` отклоняет целую позу вместо независимой обрезки суставов;
робот удерживает предыдущую полную позу и продолжает штатный подъём.
Диагностика сообщает эти два кадра. Походки и IK не переписаны.

Численные критерии симуляции зафиксированы в `scripts/sim_probe.py` и отчёте:
за 6 с движение по заданной оси >3 см, поперечное отклонение <50% продольного;
поворот в нужную сторону >0,15 рад; наклон <0,35 рад и высота >4 см после подъёма.
После 2 с остановки дрейф за последние 0,5 с <5 мм и <0,03 рад.
Это критерии работоспособности демонстрации, не точности реального робота.

Подробности: `reports/test_robot_audit.md`, `reports/STATUS.md`,
`reports/check-summary.json`, `reports/simulation.json`.

## Наглядная демонстрация

Живое окно PyBullet использует тот же MotionController и исходную URDF:

```sh
.venv/bin/python scripts/visual_demo.py
```

W/S — вперёд/назад, A/D — влево/вправо, Q/E — повороты. Отпускание клавиши
останавливает ходьбу. Пробел блокирует команды движения до Enter. Клавиши 1/2/3
выбирают Tripod/Wave/Ripple: при смене робот сначала останавливается и ждёт IDLE.
Esc закрывает окно. Мышью можно рассматривать исходную модель средствами PyBullet.

Для проверки без экрана: `scripts/visual_demo.py --headless --seconds 10`
через Python окружения. Этот прогон выполнил 501 шаг и завершился в IDLE.

`visual/replay.html` — шаблон просмотра записанных результатов; команда
`python scripts/build_visual.py` собирает его с данными из `reports/simulation.json`.
В просмотре 18 сценариев (исходный yaw=0), пауза, перемотка, вид сверху и темп.
Положение корпуса взято из PyBullet; схематические ноги построены по целевым
углам, а не по измеренным положениям физических суставов. Это воспроизведение
записи, а не повторный расчёт физики в браузере.

## Интерфейс с изменяемыми параметрами

```sh
.venv/bin/python scripts/simulation_ui.py --port 8766
```

Открыть `http://127.0.0.1:8766`. Это живой расчёт исходной URDF в PyBullet,
а не воспроизведение записи. Сервер доступен только на локальном компьютере.
Если `.venv` находится в другой папке, использовать полный путь к её Python.

В интерфейсе доступны:
- кнопки вперёд/назад, повороты на месте, стоп и постоянное ускорение ×1,5;
- скорости вперёд/назад, влево/вправо и поворота; выбор Tripod/Wave/Ripple;
- трение поверхности, гравитация и начальный yaw (через «Новая сцена»);
- расстояние, поворот и наклон камеры;
- начало движения, остановка в стойке, пауза/продолжение физики и повторное разрешение;
- изображение исходной модели, состояние, модельное время, координаты и 18 целевых углов.

Все числовые параметры можно вводить вручную в полях справа от названия или
менять ползунками. Пустые поля и значения за пределами диапазона отклоняются;
дробные значения сохраняются без округления к шагу ползунка. После изменения
нажать «Применить параметры». При смене походки
контроллер сначала останавливается. «Новая сцена» сбрасывает время и положение,
применяет выбранные параметры и поднимает робота в стойку без ходьбы.
Пауза замораживает физику и логическое время; «Стоп» продолжает расчёт и
останавливает ходьбу. В ручном режиме при потере связи с интерфейсом более 2 с команда движения
снимается. В режиме кнопок/мозга направление сохраняется до следующей команды;
закрытие браузера или клиента его не отменяет. Параметры хранятся в памяти до перезапуска сервера.

Геометрия и высота стойки фиксированы. Изменённые гравитация и трение —
экспериментальные условия, не часть ранее принятой матрицы 36 сценариев.
Модель рисуется в браузере через WebGL с ограничением 60 кадров/с. Сервер
считает физику независимо от отрисовки и передаёт измеренные положения суставов
и корпуса примерно 25 раз/с; браузер интерполирует их с задержкой около 80 мс.
Исходные URDF/STL загружаются один раз с локального сервера, внешние CDN не нужны.
Камера не влияет на расчёт физики. Частота отображения зависит от GPU браузера.
Для остановки сервера нажать Ctrl+C в его терминале.

Проверка интерфейса: `.venv/bin/python tests/test_simulation_ui.py`.
Она проверяет отклонение неверных настроек, соответствие всей URDF-иерархии
измеренным положениям звеньев PyBullet, отсутствие CPU-рендеринга, реальную смену походки,
движение/остановку, паузу и сброс сцены. Результат: `reports/ui-tests.txt`.

### Замеры после WebGL

На текущем компьютере в стойке (окно 5 с): сервер использовал около 13% одного
ядра и 270 МиБ RSS; модель продвигалась на 0,995 с за реальную секунду.
До изменения: около 61% ядра, 283 МиБ RSS и 0,544 модельной секунды за реальную.
Эти цифры не включают браузер и GPU, куда перенесена отрисовка; это не оценка
суммарных ресурсов и не замер на Repka Pi. В браузере отображается текущий FPS.

### Независимый запуск сервера

Чтобы сервер не завершался вместе с временной сессией терминала/чата,
запускайте его как пользовательскую службу systemd:

```sh
bash scripts/server.sh start
bash scripts/server.sh status
bash scripts/server.sh logs
bash scripts/server.sh restart
bash scripts/server.sh stop
```

При наличии `.venv` в корне проекта переменную PYTHON можно не указывать.
Служба `muha-simulation.service` слушает только `127.0.0.1:8766`, пишет журнал
в journalctl и перезапускается через 2 с при аварийном завершении процесса.
Она не привязана к чату, но не настроена на автозапуск после перезагрузки:
после перезапуска компьютера повторите `server.sh start`.
